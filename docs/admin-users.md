# Користувачі адмінки

Підготовлено 20.10.2026. Спочатку виконайте `supabase/admin-users-upgrade.sql`.
Актуальне правило: керування користувачами доступне лише головному власнику
`bodyasv@gmail.com` із чинною роллю `owner`. Інші власники працюють із магазином,
але не можуть читати список адмін-користувачів, запрошувати чи редагувати їх.
Назва «Головний власник» в інтерфейсі — додаткова ознака цього акаунта, не нова
роль enum. Призначення іншим людям ролі `owner` не передає керування користувачами.

Для наявної бази після `admin-users-edit-upgrade.sql` виконайте
`admin-users-chief-owner-upgrade.sql`. Він повторювано посилює всі п’ять RPC,
перевіряє наявність саме цього власника та не змінює профілі, email чи паролі.
Якщо акаунт не знайдено серед власників, міграція зупиняється без автоматичного
підвищення ролі. API окремо перевіряє email із перевіреного Auth user, не з body.
Оновлені початкові міграції зберігають це правило і при повторному виконанні.

Для SQL Editor доступні файли `admin-users-edit-sql-editor.sql` та
`admin-users-chief-owner-sql-editor.sql` у тому самому порядку. Вони не використовують
доларове цитування. Edit-версія також не використовує SELECT INTO для змінних:
у користувацькому середовищі навіть окремий DO-тест із SELECT 1 INTO v_probe
повернув relation v_probe does not exist. Натомість застосовано присвоєння
результату скалярного підзапиту; FOR UPDATE та перевірка відсутнього користувача
збережені. Точний компонент, який неправильно обробляє початковий тест, не встановлено.
Він не створює й не змінює ролі наявних людей. Наприкінці показує кількість
власників та менеджерів. Має бути щонайменше один чинний власник; якщо owners=0,
потрібно окремо підтвердити, якому наявному профілю надати роль власника.
Автоматичного призначення першого власника немає.

## Можливості

- Розділ `admin#adminUsers`: список користувачів / незавершених запрошень,
  ім’я, email, роль, стан, дата останнього входу в серверній відповіді.
- Додавати можна менеджера (типово) або власника. Менеджер зберігає всі чинні
  права роботи з каталогом, контентом і замовленнями; granular RBAC тут не додається.
- Тільки головний власник може запрошувати людей і читати список із email.
- Перед запрошенням потрібні checkbox і підтвердження email та ролі. Сервер
  повторно перевіряє JWT, роль та підтвердження. Браузеру не довіряється actor UUID.
- Видалення акаунтів і встановлення чужих паролів власником не передбачені.
  Для вже активних користувачів повторне запрошення не використовується.

## Створення та пошта

Сервер `/api/admin-users` використовує наявний SUPABASE_SERVICE_ROLE_KEY, який
ніколи не передається браузеру. Створює Supabase invitation link через generateLink,
атомарно прив’язує новий профіль до ролі, потім надсилає фіксований шаблон через
наявну Microsoft 365 / `MS_GRAPH_CLIENT_SECRET` із office@tehnoroom.com.ua.
Звичайні листи замовлень і надалі мають фіксованого одержувача office@tehnoroom.com.ua.
Зміни SMTP, OAuth-дозволів або облікових даних не потрібні й не виконуються.

Redirect фіксований: `https://www.technoroom.com.ua/admin` (той самий, що для відновлення пароля).
Ця адреса має бути дозволена в Supabase Auth → URL Configuration → Redirect URLs.
Якщо Supabase підміняє redirect на іншу адресу, перевірка посилання блокує лист.
Не передавайте посилання через чат/логи: воно містить одноразовий секрет.
У журналі зберігається лише стан, а не посилання чи пароль.

Новий користувач відкриває лист і сам задає пароль (від 10 символів), після чого
виходить із сеансу та входить звичайним способом. Invite type з callback hash захоплюється
до ініціалізації Supabase, щоб dashboard не перекрив форму пароля.
Помилки встановлення пароля не трактуються як успіх.

Виправлення 20.10.2026: `type=recovery`, як і `type=invite`, захоплюється
до створення Auth-клієнта. Перевірка режиму повторюється після кожного
асинхронного читання користувача / профілю, щоб запізніле відкриття dashboard
не перекрило форму нового пароля. Звичайний вхід залишається без змін.
Це не створює акаунтів і не змінює жодного пароля автоматично.

`202 accepted` означає прийняття Microsoft, не підтвердження доставки адресату.
Перевіряти реальне надсилання потрібно лише після вибору власником реальної адреси
та ролі; автоматичних тестових запрошень у продакшні немає.

## Редагування користувачів

Додатково виконайте `supabase/admin-users-edit-upgrade.sql` (після основної міграції).
Міграція сама не змінює жодних даних користувачів.
Кнопка «Редагувати» дозволяє головному власнику заповнити / змінити ім’я та роль наявного
користувача. Email, Auth metadata та пароль не змінюються; листи не надсилаються.
Власну роль змінювати заборонено, останній власник має залишитися. Незавершені
запрошення не редагуються, щоб дані в листі не суперечили доступу.
Зміни підтверджуються разом з email цільового акаунта, старою і новою роллю.
Сервер отримує actor тільки з перевіреного JWT; SQL повторно перевіряє власника.
RPC доступний лише service_role; редагування ролей серіалізоване, перевіряється
початкове ім’я / роль (захист від перезапису чужої зміни).
Журнал `admin_user_change_log` зберігає автора, ціль, старі та нові ім’я / роль
і час. Прямий доступ із браузера до журналу заборонено.

## Повторні спроби запрошень

Створення Auth-акаунта, запис профілю й зовнішній лист не є однією транзакцією.
Тому є lease із attempt UUID, журнал станів і захищене повторне надсилання.
Чужий наявний Auth-акаунт без власного журналу не отримує доступ автоматично.
Крах після генерації посилання розпізнається за marker UUID в user metadata,
який ніколи сам по собі не визначає права. Права задає лише профіль.
Прив’язка повторно перевіряє власника, email, lease та цільовий акаунт.
Наявні ролі й профілі не перезаписуються.

Повтор доступний лише до першого входу, із затримкою 60 секунд; незавершений
lease може триматися 10 хвилин. Ліміт — 20 нових email за добу на власника.
Стара роль запрошення незмінна. Повторне посилання використовує recovery flow
для того самого, вже створеного запрошенням користувача.
При неоднозначній мережевій помилці спершу перевірити пошту; автоповтору немає.

## Захист прав

У старій схемі `UPDATE profiles` для себе дозволяв змінити role. Міграція
забирає table/column UPDATE для role/id/created_at, залишаючи лише UPDATE(full_name)
під чинною RLS-політикою власного профілю. INSERT/DELETE для браузера заборонено.
Службові RPC доступні тільки service_role, а всередині перевіряють роль p_actor.
Переданий браузером UUID власника не дає доступу: authenticated не має EXECUTE.
Журнал не читається anon/authenticated напряму. API — POST, no-store,
із перевіркою Origin та owner. Жодних service-role ключів, токенів, invite URL
або сирих помилок поштового сервера в UI/журналах немає.

## Перевірка

`node --test tests/admin-users.test.mjs` перевіряє справжнім PostgreSQL-двигуном
повторюваність SQL, self-promotion denial, name editing, owner/service права,
email ownership, lease/cooldown та повтори. Моками перевіряються API, mail recipient,
фіксований redirect, очищені помилки, password setup та HTML escaping.
`node --test tests/*.test.mjs` — регресійний набір.
До публікації потрібно застосувати міграцію та звірити owners>0.
