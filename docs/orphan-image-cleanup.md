# Одноразове очищення підтверджених фото, 20.10.2026

Сторінка `/orphan-image-cleanup.html` підготовлена для підтвердженого користувачем
набору **1877 файлів / 755051158 байтів**. Не є загальним автоматичним очищувачем.
Початковий результат SQL: 5008 об’єктів / 1440445845 байтів. Очікуваний залишок
після саме цієї операції: 3131 об’єкт / 685394687 байтів, якщо інших змін немає.
Шість інших невикористаних фото (1091961 байт) та неоднозначний файл не чіпаються.

Використовує поточну адмін-сесію Supabase на тому самому origin; не читає/показує
токени і не потребує service-role ключа або нових SQL-функцій. Перевіряє getUser
та is_admin, а Storage RLS залишається чинним. За відсутності доступу зупиняється.

1. Не запускати імпорт/редагування в інших вкладках під час перевірки й очищення.
2. Перевірити список. Читаються всі продукти (включно з прихованими/варіантами),
   категорії, бренди, банери, статті та файли безпосередньо у папці products.
3. Кандидати — лише стандартні `products/import-ID-timestamp-index.ext`,
   ID яких відсутній у products, без жодної згадки basename у поточних даних,
   старші 24 годин і з повними метаданими. Копії карток в окремій backup-таблиці
   не є поточними посиланнями сайту і не утримують файли від очищення.
4. Кількість та сума байтів мають точно дорівнювати підтвердженим. Інакше стоп.
5. Завантажити JSON-маніфест. Це список для звірки, НЕ резервна копія зображень.
6. Позначити попередження, ввести `ВИДАЛИТИ 1877`, натиснути видалення та
   підтвердити діалог. Саме відкриття/перевірка сторінки не видаляє файлів.
7. Перед кожним пакетом до 500 файлів перечитуються посилання й метадані.
   Будь-яка зміна залишку маніфесту зупиняє операцію. Використовується тільки
   Supabase Storage remove API, НЕ SQL DELETE FROM storage.objects.
8. Неповна/помилкова відповідь зупиняє операцію, повторення без аудиту заборонене.
   Частина файлів при цьому вже могла бути видалена: Storage не є транзакцією
   для всіх 1877 об’єктів. Після успіху список повторно перечитується і жоден
   об’єкт маніфесту не повинен залишатися.
9. Завершити повторним SQL-підрахунком сховища та зберегти журнал результату.

Між перевіркою й Storage API є невелике вікно конкурентного редагування;
тому необхідно призупинити ручне редагування та імпорти. Нових блокувань/змін
прав доступу сторінка не додає. Після часткового успіху початковий ліміт 1877
спеціально не дозволить бездумно повторити операцію.

Публікація сторінки не означає виконане очищення. До результату Storage API
та фінального підрахунку не повідомляти, що фото видалено.
